## 2026-04-04 20:09 — Сессия: архитектура оркестрации + LightRAG decision

### Контекст: Orchestrator/Executor/Critic architecture
Макс нашёл/сформулировал модель системы управления агентами:
- Orchestrator: планирование, что дальше, не делает задачи
- Executor: делает конкретные задачи
- Critic: проверяет результат, verdict
- Workflow: REQUIREMENTS → PLANNING → EXECUTION → REVIEW → DONE

### Мои замечания (critical analysis):
- "3 роли одной моделью" — компромисс, не цель. Разные режимы требуют разных temperature/моделей
- Notion НЕ подходит для machine-readable state — таблица, не БД. Для MVP ok, для scale — узкое место
- "Workflow важнее модели" incomplete — нужен ещё tooling (capabilities)
- Minimal MVP = одна работающая итерация, не три роли
- Не хватает: communication layer, error recovery, checkpointing

### Решения принятые:
1. **Portability важнее cloud** — Notion отпадает для онтологии (медленный)
2. **LightRAG** — выбран как базовая технология (open source, self-hosted)
3. **VPS-based** — всё на VPS (есть), платим за VPS + LLM токены
4. **Embedding локально** — sentence-transformers на CPU (бесплатно)
5. **LLM API = MiniMax** — текущий провайдер, устраивает

### LightRAG (ключевой reference):
- Open source RAG engine с graph extraction + vector search
- Self-hosted, free
- Сущности + связи + вектора
- Use case: файл с воспоминаниями → агент автоматически раскладывает в узлы графа

### Архитектура стека:
```
VPS
├── LightRAG (self-hosted)
│   ├── Graph storage (SQLite/files)
│   └── Vector index (Chroma local)
├── Embedding: sentence-transformers (CPU, ~$0)
└── LLM: MiniMax API (~$20-30/month total)

Telegram → Calen → LightRAG API → Graph + Vectors
```

### Use cases определённые:
1. Файл воспоминаний о предках → graph nodes (люди, места, события, связи)
2. Векторный поиск по онтологии
3. Philosophic notes → extraction в ontology
4. Цитаты → "эту ценность разделяю" → personality node
5. Health/diet data НЕ трогаем (работает, sensitive)

### Наследнический аспект:
- Portability = контейнер/папка которую можно передать
- Raw files важны (наследник читает оригинал)
- Graph = machine-readable, для агента

## 2026-05-25 18:57 EEST — Размышление: PKM state vs UserData как отдельные классы данных

В рамках этого проекта появился еще один важный архитектурный слой для размышления. В процессе работы сначала с OpenClaw, а теперь с Hermes, у меня сформировался слой UserData. В Hermes для него уже есть отдельная одноименная папка. В нашей архитектуре это layer 3: он не версионируется, а бэкапится.

Это важно сопоставить с PKM. База знаний, которая формируется в рамках проекта PKM, по своей природе тоже всё больше выглядит как state системы, а не как проектный артефакт. То есть её роднит с UserData то, что:
- эти данные не должны жить как обычный versioned project content;
- эти данные логичнее бэкапить, чем полноценно вести через git;
- для них нужен отдельный разговор о синхронизации и переносимости.

Но между ними есть и принципиальная разница. UserData изначально собирался как серверный слой:
- данные хранятся на VPS;
- агент работает с ними круглосуточно;
- локальная копия на пользовательских устройствах для работы не нужна.

PKM-state другой:
- знания, заметки, концепты и связи хочется просматривать и, возможно, редактировать с разных устройств;
- сюда уже подключается Obsidian и человеческая работа с knowledge base;
- поэтому здесь вопрос синхронизации между устройствами существенно важнее, чем для UserData.

Отсюда вопрос для архитектуры: стоит ли использовать UserData как место для PKM-state, или не стоит. На первый взгляд их объединяет общий класс: non-versioned backed-up state. Но operationally это всё же не одно и то же. UserData — сервероцентричный runtime/data слой для постоянной агентной работы. PKM — knowledge layer, который требует не только backup, но и удобного межустройственного доступа для человека.

То есть вопрос не только в том, versioned это или non-versioned. Вопрос в способе жизни данных:
- server-only operational state;
- или human-facing knowledge state with cross-device access.

Нужно отдельно продумать, должны ли PKM-state и UserData жить:
- в одной общей non-versioned data domain;
- в двух разных хранилищах с разной operational model;
- или в общей архитектуре, но с разными правилами sync, backup и доступа.
